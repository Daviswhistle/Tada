# Encrypted record backup

The settings page **내 기록 → 백업 파일 만들기** creates an encrypted `.tadabackup` download from the continuing conversation. The same page offers **백업에서 기록 복원** through the application setup coordinator. Preview is read-only; explicit confirmation drains the current runtime, reconnects the account and opens a separate journal. Backup creation alone is not release qualification or a successful restore.

The browser offers an explicit download link after creation; it does not claim the browser has saved the file. Ordinary backup requires no new password. A fresh random archive key is protected with the current Windows user's DPAPI, including the supported WSL route. An optional generated recovery code can open that one archive independently of Windows. Store it separately from the archive; both together expose its records. The code is displayed only during that settings session, is not stored on the host and is cleared on close or device disconnection. Closing before acknowledging code storage prompts once. Losing both the original OS protection and the code makes the archive unreadable.

## Data and authority

One SQLite read transaction exports all rows, not the paginated UI view. The explicit table/column allowlist includes device labels, turns and document revisions, request usage, follow-up proposals/work/notices/reviews, proactive-origin markers, browser action records, mail drafts/action outcomes, and Telegram delivery records. Their saved states and relationships are preserved, including queued work and uncertain outcomes. Creating a backup does not modify them or suspend an already running task.

The archive excludes reusable connection credentials, device authentication hashes, setup/pairing tokens, Telegram bindings and controls, provider checkpoints, and executable settings/grants. Provider account identity/model, its public subscription registration identifier, and Tada's dedicated Google OAuth client configuration can be included inside the ciphertext to support reconnection. Subscription access/refresh/ID tokens and the old host identifier are excluded. User-written record content is not a secret scrubber: anything the user typed into a conversation remains conversation data.

**An archive is data, never permission to resume work.** It cannot establish whether an action was sent, canceled, changed or deleted after the backup. A restore must validate every domain and relationship, create a new journal/key and fresh account connections, retain source lineage, and quarantine historical work against execution before enabling any runtime. The application coordinator implements that separate boundary. `openRecordBackup` authenticates/decrypts the data format and checks structural references; it does not import a database or authorize dispatch. Do not feed its output to a live store without that separate restore boundary.

## Format and bounds

`TADA-BACKUP-1\n`, a four-byte big-endian header length, a strict JSON header, and an AES-256-GCM envelope. The header contains version, DPAPI-wrapped archive key, optional recovery-code wrapper and plaintext length. All header bytes are authenticated as additional data. The archive key is independent of the original database key. Recovery codes contain 192 random bits; HKDF-SHA-256 derives a wrapper key with a per-archive salt and domain separation. No plaintext archive is written by the host.

Plaintext is bounded to 32 MiB; the header to 16 KiB, each table to 100,000 rows and total rows to 200,000. Exceeding a bound fails explicitly without producing a partial file. The archive parser rejects duplicate keys, malformed Unicode, non-finite numbers and nesting deeper than 64. Its larger bound does not widen the existing JSON wire readers. Unknown fields/versions and altered ciphertext are rejected. Selecting a wrong recovery code never silently falls back to Windows protection.

The authenticated same-origin POST requires explicit backup consent, returns `no-store` binary content and rechecks the device and host after the asynchronous DPAPI operation. Only one archive is created at a time. Device revocation or shutdown prevents a late private response; graceful shutdown drains admitted backup creation. The browser bounds both headers and body waiting, aborts on close, revokes temporary object URLs and ignores stale responses. No model tool can create or receive backups.

## Isolated recovery records (DB v7 foundation)

A fresh `ContactStore` can now accept a validated archive through the internal `recovery` initialization option. This is the storage and read-path foundation used by the application coordinator below. Do not replace an existing journal with this constructor or bypass the coordinator when switching the active installation.

The immutable v1–v6 schema strings are preserved. Recovery initializes a new v7 database and journal identity. Historical rows are encrypted in a separate `restored_records` namespace, authenticated against a sealed generation manifest. They never enter executable turns, requests, devices, follow-ups, reviews, Telegram outbox, mail actions, settings or provider checkpoints. Removing or changing an archived row fails reopening. Existing v1–v6 journals are not silently upgraded.

Command lookups (`turn`, `followup`, `mailAction`, `browserActions`) remain current-generation-only. Explicit read paths merge conversation, document, mail and past-work records with the source journal and backup timestamp. Old running/queued states remain their **backup-time observations**; they are not rewritten as present activity or completion. Old device tokens are not restored. Old request IDs cannot be resubmitted. New request/turn sequence numbers exceed historical IDs; old inference usage is shown separately from current execution allowance. Owner-intent context, automatic checks and reminder dispatch use only the active namespace.

A new request may read an old document and save a new revision, retaining its parent, root, content hash and references across restart. Historical mail reads return saved observations without Gmail reconciliation. Old mail/work IDs cannot be adopted by granting new account or device permissions. Unresolved browser effects still block new writes to their origin; a fresh explicit owner acknowledgement is recorded separately and permits new work without changing the historical receipt.

Archive payload v2 adds a flat list of historical generations for rebackup. Payload v3 additionally preserves `provider.client_id` (null for local models), keeping the subscription's workspace-bound registration while allocating a fresh host and tokens. It supports source schemas 1–7, with historical groups only on v7, and accepts flat v1/v2/v3 history. Original v1/v2 field sets stay unchanged; old readers reject v3 rather than ignoring its binding. The binary encryption envelope remains version 1. Original v1 payloads retain their exact interpretation, while v2 is limited to v7 source journals and rejects recursive histories. The importer validates IDs, domain payloads, references, document lineage and action receipts before creating storage. Bounds remain 32 MiB and 200,000 total records, across all historical and current generations. Backup creation checks the same flattened size and total record limits as import, so repeated recovery cannot produce an archive that exceeds import bounds. It does not infer effects that happened after the snapshot.

Synthetic recovery checks cover execution isolation, old-token rejection, quotas and owner-context separation, blocked old follow-up/mail/delivery calls, document revision/restart/rebackup, retained uncertain browser effects, explicit acknowledgement, encrypted archive round trips, calendar provenance, pagination and tamper rejection. These do not establish owner-data migration, physical cross-computer recovery or a completed release.

The latter retain their known effect while separately requiring a current site check before new work.

Recovered citation IDs reserve their original numbers before any fresh model observations, without importing model checkpoints or old owner context. Conflicting receipts and unsafe counters are rejected. ## Application restore

`npm start` and the installed launcher retain the same stable application lease and background-start arguments during restoration. From **내 기록**, the owner chooses a `.tadabackup`, optionally supplies its recovery code, and sees the timestamp, account and record counts before choosing **이 기록으로 복원**. The ordinary current conversation remains running during preview. The conversation hands back only the setup screen location, never its installation capability. Restoration uses the original launch authority already held in that computer browser; a paired conversation device does not gain it. A browser without that authority must reopen Tada from its normal launcher. Top-level document navigation works from HTTP and HTTPS conversation pages, while APIs still require the local capability and same origin. The setup API checks the capability, origin, content type, byte limit and state revision; preview expires after ten minutes. File bytes and recovery codes are never placed in URLs or logs.

Confirmation re-encrypts the snapshot under a fresh archive key protected by the current Windows account and persists a staged generation in `DATA.app-private/records`. Then setup stops admission and drains/closes the old runtime while retaining its application lease. A fresh storage key and profile are created in that generation. For v3 subscription archives, login reuses the issued client ID and must return the saved subject; another user or registration cannot receive the records or replace that binding. Legacy v1/v2 backups lack the workspace registration: the preview explicitly explains that reconnecting requires choosing a workspace, its usage/privacy settings apply, and the confirmation is labeled **워크스페이스를 새로 연결해 복원**. The old subject is still checked when present; matching it alone does not establish the old workspace. Existing tokens are not copied. An unavailable saved or launch-argument model is chosen on screen. A private versioned generation record binds that selection to the original model argument, so the same launcher continues with the chosen model on restart. A deliberately different later model argument is not silently overridden. This selection file contains no credentials and does not change the provider-profile format. Local-model restores use the selected local runtime, with their key stored at a stable generation location. Google client registration metadata is reprotected, but account tokens, device pairings, automatic checks and dispatch grants remain absent.

Every not-yet-active restoration attempt gets a fresh isolated candidate directory; a candidate is published as the generation's conversation only after its store is fully initialized and closed. A previously prepared but inactive database is preserved separately after checking its ownership lease. This allows the selected model or catalog to change between retries without rewriting an active journal route. Before serving or starting any work, activation first acquires the original journal/profile ownership locks, including a previous restored generation. An independently running contact CLI blocks the switch. POSIX retains those locks through activation; on Windows, source locks are checked before moving and the OS rejects directory moves while any competing SQLite handle remains open. Activation preserves the original default data and key/profile directories by whole-directory rename on the same volume. Their original paths become exclusive file barriers, so supported older normal launchers cannot revive old queues or silently initialize a replacement. When the old data directory is absent, a guard is installed before moving the profile. Trees are checked before and after their moves; top-level SQLite ownership-lease sidecars are validated as private files before SQLite opens them, but their transient bytes are excluded from the durable source fingerprint; changed sources, symlinks, collisions, different volumes or held Windows handles fail without copy/delete fallback. Each barrier is fully written and flushed at a private preparation name, then published with an atomic, no-overwrite hard link. If interrupted between publication and preparation-name cleanup, only that exact two-link inode and barrier content are admitted for cleanup. Empty or partial original-path files are never published. The active generation pointer is replaced only after both paths are blocked. Every recorded move/pointer boundary can be retried from its durable phase without restarting historical work.

Cancel during account reconnection, or after a failed reconnect before activation, returns to the original conversation. Once preservation begins, setup offers retry instead of undoing partially completed moves. Staged/canceled snapshots and preserved originals remain encrypted/private and are retained; this is not erasure or merging. A missing active journal or changed barrier stops startup rather than creating a blank replacement. Direct advanced CLI access to manually chosen archived paths and malicious same-user filesystem modification are outside the normal-launcher rollback claim. File flushing does not establish Windows power-loss durability of directory rename.

Synthetic integration tests exercise actual subscription OAuth/JWT identity checking, fresh protected keys, Google client configuration, real CLI/store startup, restart and local-model HTTP inspection, with external destinations rejected. Filesystem tests cover both present/missing original data, each durable switch boundary, partial initialization, repeated restoration, cancellation, path collisions and linked/changed sources. Browser-client tests cover stale preview results, file replacement, authorization loss and the account/cancel/redirect flow. These checks do not migrate the owner's live journal or establish physical cross-computer recovery.

The registration boundary follows OpenAI's [profiles and sessions documentation](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions) and [sign-in protocol](https://developers.openai.com/siwc/token-sharing-open-source/sign-in): an issued client ID binds a user and workspace, while `sub` and email alone do not identify a workspace. Public registration metadata is preserved; authentication is performed again. Synthetic OAuth tests reject a changed registration before exchanging the code, reject a changed subject before model/catalog use, and verify returning sign-in plus restart. Mixed legacy/v3 records survive repeated recovery and encrypted rebackup without flattening away their provenance.
