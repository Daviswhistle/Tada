# Encrypted record backup

The settings page **내 기록 → 백업 파일 만들기** creates an encrypted `.tadabackup` download from the continuing conversation. This slice preserves records; application-level restoration is not implemented yet. Keep the original journal. Backup creation alone is not a release qualification or a successful restore.

The browser offers an explicit download link after creation; it does not claim the browser has saved the file. Ordinary backup requires no new password. A fresh random archive key is protected with the current Windows user's DPAPI, including the supported WSL route. An optional generated recovery code can open that one archive independently of Windows. Store it separately from the archive; both together expose its records. The code is displayed only during that settings session, is not stored on the host and is cleared on close or device disconnection. Closing before acknowledging code storage prompts once. Losing both the original OS protection and the code makes the archive unreadable.

## Data and authority

One SQLite read transaction exports all rows, not the paginated UI view. The explicit table/column allowlist includes device labels, turns and document revisions, request usage, follow-up proposals/work/notices/reviews, proactive-origin markers, browser action records, mail drafts/action outcomes, and Telegram delivery records. Their saved states and relationships are preserved, including queued work and uncertain outcomes. Creating a backup does not modify them or suspend an already running task.

The archive excludes reusable connection credentials, device authentication hashes, setup/pairing tokens, Telegram bindings and controls, provider checkpoints, and executable settings/grants. Provider account identity/model and Tada's dedicated Google OAuth client configuration can be included inside the ciphertext to support a future reconnect flow. User-written record content is not a secret scrubber: anything the user typed into a conversation remains conversation data.

**An archive is data, never permission to resume work.** It cannot establish whether an action was sent, canceled, changed or deleted after the backup. A future restore must validate every domain and relationship, create a new journal/key and fresh account connections, retain source lineage, and quarantine historical work against execution before enabling any runtime. `openRecordBackup` authenticates/decrypts the data format and checks structural references; it does not import a database or authorize dispatch. Do not feed its output to a live store without that separate restore boundary.

## Format and bounds

`TADA-BACKUP-1\n`, a four-byte big-endian header length, a strict JSON header, and an AES-256-GCM envelope. The header contains version, DPAPI-wrapped archive key, optional recovery-code wrapper and plaintext length. All header bytes are authenticated as additional data. The archive key is independent of the original database key. Recovery codes contain 192 random bits; HKDF-SHA-256 derives a wrapper key with a per-archive salt and domain separation. No plaintext archive is written by the host.

Plaintext is bounded to 32 MiB; the header to 16 KiB, each table to 100,000 rows and total rows to 200,000. Exceeding a bound fails explicitly without producing a partial file. The archive parser rejects duplicate keys, malformed Unicode, non-finite numbers and nesting deeper than 64. Its larger bound does not widen the existing JSON wire readers. Unknown fields/versions and altered ciphertext are rejected. Selecting a wrong recovery code never silently falls back to Windows protection.

The authenticated same-origin POST requires explicit backup consent, returns `no-store` binary content and rechecks the device and host after the asynchronous DPAPI operation. Only one archive is created at a time. Device revocation or shutdown prevents a late private response; graceful shutdown drains admitted backup creation. The browser bounds both headers and body waiting, aborts on close, revokes temporary object URLs and ignores stale responses. No model tool can create or receive backups.

## Isolated recovery records (DB v7 foundation)

A fresh `ContactStore` can now accept a validated archive through the internal `recovery` initialization option. This is the storage and read-path foundation; the ordinary application does **not yet offer restore/import**, reconnect accounts, or switch the active installation. Do not replace an existing journal with this constructor. The setup coordinator and rollback-safe installation transition remain separate required work.

The immutable v1–v6 schema strings are preserved. Recovery initializes a new v7 database and journal identity. Historical rows are encrypted in a separate `restored_records` namespace, authenticated against a sealed generation manifest. They never enter executable turns, requests, devices, follow-ups, reviews, Telegram outbox, mail actions, settings or provider checkpoints. Removing or changing an archived row fails reopening. Existing v1–v6 journals are not silently upgraded.

Command lookups (`turn`, `followup`, `mailAction`, `browserActions`) remain current-generation-only. Explicit read paths merge conversation, document, mail and past-work records with the source journal and backup timestamp. Old running/queued states remain their **backup-time observations**; they are not rewritten as present activity or completion. Old device tokens are not restored. Old request IDs cannot be resubmitted. New request/turn sequence numbers exceed historical IDs; old inference usage is shown separately from current execution allowance. Owner-intent context, automatic checks and reminder dispatch use only the active namespace.

A new request may read an old document and save a new revision, retaining its parent, root, content hash and references across restart. Historical mail reads return saved observations without Gmail reconciliation. Old mail/work IDs cannot be adopted by granting new account or device permissions. Unresolved browser effects still block new writes to their origin; a fresh explicit owner acknowledgement is recorded separately and permits new work without changing the historical receipt.

Archive payload v2 adds a flat list of historical generations for rebackup. The binary encryption envelope remains version 1. Original v1 payloads retain their exact interpretation, while v2 is limited to v7 source journals and rejects recursive histories. The importer validates IDs, domain payloads, references, document lineage and action receipts before creating storage. Bounds remain 32 MiB and 200,000 total records, across all historical and current generations. Backup creation checks the same flattened size and total record limits as import, so repeated recovery cannot produce an archive that exceeds import bounds. It does not infer effects that happened after the snapshot.

Synthetic recovery checks cover execution isolation, old-token rejection, quotas and owner-context separation, blocked old follow-up/mail/delivery calls, document revision/restart/rebackup, retained uncertain browser effects, explicit acknowledgement, encrypted archive round trips, calendar provenance, pagination and tamper rejection. These do not establish owner-data migration, physical cross-computer recovery or a completed release.

Foundation validation on 2026-10-10: the final amended full check passed 1,225 tests with no skips. An earlier full run exposed a test double still implementing the old read interface; it was updated to the new explicit read-only method without weakening assertions. Native Windows passed 145 applicable recovery/backup/browser/public-research checks, plus real DPAPI and portable archive key round trips, with tested source byte parity. A separate localhost browser showed restored running work as historical and offered no cancel/retry control. These fixtures made no live model or account calls. Dependencies, Rust contracts and native executables are unchanged; previous required results remain applicable.

Recovery compatibility also covers legacy Telegram payloads predating multipart group identifiers, dedicated Google client configuration on a fresh v7 journal, and historical applied-mismatch receipts. The latter retain their known effect while separately requiring a current site check before new work.

Recovered citation IDs reserve their original numbers before any fresh model observations, without importing model checkpoints or old owner context. Conflicting receipts and unsafe counters are rejected. Explicitly retrieved archived document references are verified as saved snapshots, not current external facts; fresh-source checks remain unchanged. Actual conversation-loop regressions cover both read orders, document revisions, historical public reports, restart and rebackup.

Citation title and URL limits use the existing runtime character bounds, including multibyte Korean text, while the archive retains its aggregate byte limits. Normal producer output at those bounds survives recovery and restart; over-limit fields remain rejected.
