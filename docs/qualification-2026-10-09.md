# 2026-10-09 — 현재 구독 경로의 행동 평가

사용자가 선택한 Tada 소유 ChatGPT 구독 프로필의 `gpt-6-astra`로 A10·A15·A16을 각각 두 고정 변형씩 실행했다. 실제 ContactService v5, SQLite와 Rust 읽기 중개기를 사용했으며 자료는 합성 파일이다. 모델에는 일반 사용자 발화와 허용 도구만 전달했다. 사례 ID·판정 기준·정답은 평가기에만 있었다. 계정·모델·결제 방식을 바꾸지 않았다.

## 관측과 수정

첫 실행은 실제 추론 26회로 모두 답변했지만 A15 첫 변형에서 무관한 `other-project.md` 본문까지 읽었다. 요약 자체는 정확하고 민감 파일 접근도 없었으나, 필요한 자료만 읽는 완료 조건을 만족하지 못했다. 독립 검수와 주 세션 모두 6변형 중 5개 통과·1개 실패로 판정했다. 당시 자동 검사에는 무관한 비민감 파일 읽기가 빠져 있었으므로 자동 검사 통과를 의미 판정으로 대신하지 않았다.

제품의 일반 지침을 관련 대상부터 읽고 구체적인 정보 공백이나 필요한 비교가 있을 때만 범위를 넓히도록 수정했다. 특정 문구·파일명·사례 ID를 분기 조건으로 넣지 않았다. 평가기의 A15 검사는 원래 완료 기준에 따라 대상 이외의 본문 읽기도 기록한다. 기존 문맥 한도를 높이거나 과거 결과를 지우지 않았다.

수정 후 같은 여섯 변형을 새로 실행했다. 실제 추론 26회가 모두 관측됐고, 대상 문서를 스스로 찾아 근거를 재확인했다. A15 두 변형 모두 대상 본문 하나만 읽었다. 별도 수락 감사자와 주 세션이 답변·관측·질문을 직접 대조해 모두 통과로 판정했다.

## 평가 경로 검수에서 발견한 차이

후속 코드 검수에서 평가 어댑터가 공급자 식별 정보를 전달하지 않은 사실을 발견했다. 그 결과 실제 구독 서비스에서 사용할 수 없는 예약 로컬 재확인이 모델에게 가능한 기능으로 안내됐다. 위 답변·읽기 관측과 의미 판정은 보존하지만 실제 운영 프로필의 수락 근거로 확정하지 않는다. 어댑터는 공급자 식별을 그대로 전달하고 서비스의 공급자·예약 재확인 가능 여부를 결과에 기록해 불일치를 거절하도록 수정했다. 수정한 경로를 같은 여섯 변형으로 다시 실행했다. 실제 요청 25회가 모두 관측됐으며 모든 변형에서 `provider: chatgpt-subscription`, `local_reviews: false`를 확인했다. 필요한 대상만 읽고 인용을 재확인했으며 모든 자동 검사와 주 세션의 의미 판정을 통과했다. 독립 감사자도 원문·도구 호출·프로필·요청 원장을 대조해 여섯 변형 모두 통과로 판정했다. 이 단계의 사례 단위 수락은 A10·A15·A16이며 전체 16건 중 나머지 13건은 미실행이었다.

## 관련 메일·답장 이력 기능 검증

관련 메일 탐색을 별도로 켠 합성 환경에서 실제 선택 모델로 세 조건을 실행했다. 실제 GoogleConnection·GoogleSources·ContactService·암호화 SQLite 경로를 사용하며 Google 응답만 합성했다. 각 조건은 실제 요청 3회씩, 합계 9회가 관측됐고 미확인 요청은 없었다. 모두 운영과 같은 구독 프로필이며 예약 로컬 재확인은 꺼져 있었다.

- “내일 오로라 미팅 준비 좀 해줘.”: 한 달 전 안건과 현재 일정을 찾아 준비안을 만들고, 이미 확정한 인원·장비를 다시 묻지 않았다. 관측 사실과 진행 제안을 구분했으며 인용 자료를 최종 재확인했다.
- 이미 답변하고 상대방도 확인한 요청: 자동 확인에서 보낸 답장과 후속 확인을 읽고 조용히 종료했다. 최종 인용이 없는 무알림 결과이므로 `verification: not_applicable`이며 최종 인용 재확인 통과로 세지 않는다.
- 답변 뒤 새 요청이 온 경우: 자동 확인에서 새 프로젝터 필요 여부와 그 기한만 제안했다. 완료된 인원·노트북 확인을 반복하거나 발신했다고 주장하지 않았다. 인용 자료를 최종 재확인했다.

주 세션과 독립 수락 감사자가 [실행 원문](../evals/assistant-v1/results/2026-10-09-related-mail.json)을 대조했고 [별도 판정](../evals/assistant-v1/results/2026-10-09-related-mail-review.json)에 세 조건 통과와 한계를 기록했다. 실제 계정의 새 탐색 권한은 켜지 않았으며 실제 Gmail·휴대폰·전체 A13 수락 근거로 확대하지 않는다. 이 기능 검증만으로 전체 16건의 수락 사례를 추가하지 않았다.

수정 후 전체 Node 검사 886개가 생략 없이 통과했고 Rust 포맷·clippy·workspace 테스트와 필수 프로세스 fixture가 통과했다. 권한 회수·재부여, 계정 교체, 오래된 요청/알림 무효화, 허용한 검색어·발급한 커서·공개된 메시지 ID 경계, 소형 문맥 한도와 브라우저 켜기·끄기를 검증했다. 설정은 실제 화면에서 확인했으며 390px 레이아웃에 가로 넘침이 없었다. 이는 물리 휴대폰 수신 검증과 별개다.

커밋 검수에서는 일반 회귀 검사를 통과한 뒤에도 두 시간차 결함을 별도 합성 재현으로 발견했다. 토큰 갱신 중 별도의 관련 메일 동의 기기가 폐기·만료되면 Gmail GET 하나가 나갈 수 있었고, 일정 전송 재검증 중 메일 설정을 바꾸면 알림이 15분 지연된 뒤 일정 시작 시 억제될 수 있었다. 두 결함을 먼저 실패하는 회귀로 재현한 뒤, Gmail API의 실제 발송·응답 경계에서 추가 동의를 재확인하고 캘린더 전용 검증은 그 동의와 분리했다. 이 수정은 새 권한을 켜거나 예약을 다시 만들지 않는다. 수정 전 모델 답변의 의미 판정은 보존하되, 모델 실행 당시 커밋과 이후 권한 경계 수정을 구분한다.

다음 재검수에서는 라벨이 없는 정상 보관 메일의 선택적 `labelIds` 생략과, 정기 관측 자체가 중단됐을 때의 일정 누락도 발견했다. 정상 필드 생략은 빈 목록으로 읽되 잘못된 타입과 금지 라벨은 계속 거절한다. 메일 동의 변경·동의 기기 폐기·만료로 정기 관측이 폐기되면 현재 권한을 새로 잡아 곧 재관측하며, 이전 모델 사용량·하루 횟수·대기 간격은 되돌리지 않는다. 전송 단계뿐 아니라 알림 생성 전 관측 단계도 회귀로 검사한다.

## 미팅 준비와 주간 업무 정리

정확한 미팅명이나 자료를 지정하지 않은 A13, 준비된 할 일 목록 없이 요청하는 A14를 각각 두 변형으로 실행했다. 사용자가 선택한 같은 구독 모델, ContactService, 암호화 SQLite, Rust 읽기 중개기와 GoogleConnection을 사용했다. 일정·메일·문서·과거 대화·저장된 업무는 합성 자료이며, 실제 계정의 읽기 범위를 바꾸지 않았다. 도구·판정 정보는 평가기에만 있고 제품에는 일반 발화와 연결된 자료만 전달했다.

[첫 실행](../evals/assistant-v1/results/2026-10-09-planning-first.json)은 요청 19회가 관측됐다. A13 두 변형은 현재 일정·자료를 찾았으나 과거 대화를 읽지 않아 실패했다. A14는 저장 업무에 고객 수령을 기다린다고 적혀 있는데 확인 메일 발신자는 동료인 모호성이 있었다. 모델이 이를 보수적으로 구분한 응답을 제품 실패로 처리하지 않고, [독립 검수](../evals/assistant-v1/results/2026-10-09-planning-first-review.json)에서 두 변형을 평가 환경 문제로 보류했다. A14에는 업무 기록만으로도 우선순위를 알 수 있어, 특정 과거 검색 도구 사용을 강제한 자동 조건도 과도했다. 첫 결과와 당시 해시를 보존했다.

제품에는 개인화된 계획을 만들기 전 관련 목표·선호·결정을 기존 기록에서 조회하는 일반 지침을 추가했다. 무관한 기록은 읽지 않으며, 과거 대화가 새 권한을 주지 않는다는 원칙을 유지한다. 특정 미팅명이나 사례 발화를 분기하지 않았다. 평가기는 수락 메일의 고객 역할을 명확히 하고 A14의 과거 조회 여부를 진단 정보로 분리했다.

[수정 후 실행](../evals/assistant-v1/results/2026-10-09-planning-context.json)은 실제 요청 20회가 모두 관측됐고 미확인 요청은 없었다. 모든 변형은 운영과 같은 구독 프로필이며, 저장 업무·알림을 바꾸지 않았다. A13은 관련 과거 대화를 읽고 작은 변경 선호·철회한 안건을 현재 자료와 함께 반영했다. A14는 고객의 완료 확인, 승인 없이 발신만 한 일, 완료 뒤 새로 온 요청과 기한을 구분했고, 사용자가 직접 결정하겠다고 한 고객 우선순위만 물었다.

관측 당시 런타임은 `2c3f9de5d88cbff85e06358bd6a5495d8f9b3644`다. 평가기와 보고서 해시, 공급자 프로필, 모델 도구 호출과 관측은 보고서에 있다. 공급자 continuation 상태는 공개 보고서에서 제외했다. 전체 Node 검사 888개가 생략 없이 통과했으며, 이번 변경은 네이티브 구현·의존성을 변경하지 않아 앞 단계의 Rust·프로세스 fixture 근거가 그대로 적용된다. 현재 주간의 모든 과거 일정, 보조 캘린더, Drive·첨부 문서, 실제 휴대폰 수신·외부 발신을 검증한 것은 아니다.

주 세션과 [독립 감사자](../evals/assistant-v1/results/2026-10-09-planning-context-review.json)는 네 변형을 모두 통과로 판정했다. 현재 구독 경로의 사례 수락은 **A10·A13·A14·A15·A16, 전체 16건 중 5건**이며 다른 11건은 미실행이다. 이는 고정 합성 환경의 근거이며 제품 출시 완료 선언이 아니다.

## 자동 제안에서 과거 결정과 선호 활용

수시 확인과 지속 사용을 함께 켠 경로에 직접 대화와 같은 제한된 기록 검색을 연결했다. 실제 선택 구독 모델 `gpt-6-astra`와 ContactService·암호화 저널·GoogleSources를 사용하고 Google 응답과 대화만 합성했다. 관련 결정은 최근 모델 문맥에서 제외했으며 새 사람이 요청하지 않아도 자동 확인에서 검색할 수 있게 했다.

[실행 원문](../evals/assistant-v1/results/2026-10-09-proactive-history.json)에서는 두 상황을 각각 3응답, 총 6 observed / 0 unknown으로 처리했다. 취소를 알린 이전 대화를 찾아 이미 취소한 워크숍 제안을 조용히 억제했다. 유효한 워크숍에는 확정한 8명·휠체어 접근·자막 조건을 반영하고, 다른 행사의 일회성 20명·통역 조건은 적용하지 않았다. 현재 메일의 예약 기한을 인용 재확인했고 회신 여부는 모른다고 밝혔으며, 발신 없이 회신 초안을 제안했다. 과거 검색의 발췌에 필요한 원문이 온전히 있어 추가 상세 읽기는 필요하지 않았다.

주 세션과 [독립 수락 감사자](../evals/assistant-v1/results/2026-10-09-proactive-history-review.json)가 실제 입력·검색 결과·답변을 대조해 두 상황을 통과로 판정했다. 실행 당시 커밋은 `8215f1b`이며 실행기·보고서 해시는 원문과 판정 파일에 보존했다. 실제 공급자 식별을 전달해 구독의 로컬 예약 재확인 불가 상태가 적용됐다. 별도 execution_profile 스냅샷 검사는 실행 뒤 평가기에 추가했으며, 과거 원문을 새 실행으로 고쳐 쓰지 않았다.

평가기 준비 단계에는 연결 어댑터의 필수 메서드 누락(모델 예약 0건)과 inspect 누락(보수적으로 unknown으로 남은 예약 2건)이 있었다. 두 번째 오류는 공급자 구현의 네트워크 발송 전 검사에서 중지된 것으로 확인했다. 준비 실패 기록은 별도로 보존하고 성공 결과에 합치지 않았다. 이후 실제 실행은 공급자 확인을 먼저 거쳤다. 평가기 회귀는 공급자 식별 보존, 계정 라벨·continuation 비공개, oracle 비노출, 미흡한 합성 답변을 성공으로 승격하지 않는 것을 검사한다.

이 근거는 합성 자료의 두 고정 상황이며 실제 Gmail·휴대폰 전달·장기 운영의 합격이 아니다. 조용한 취소 결과는 외부 취소 확인을 뜻하지 않는다. 정식 16건의 신규 사례 수락으로 세지 않으며 현재 5건 통과·11건 미실행 상태를 유지한다.

최종 Node 검사 905개가 생략 없이 통과했다. 기록 조회의 페이지·잘림·재시작, 수시 확인/지속 사용 조합, 권한 해제·새 사용자 발화 뒤 조회 및 결과 차단을 포함한다. 네이티브 구현과 계약 스키마·의존성은 이번 변경에서 동일하므로 앞서 통과한 Rust·프로세스 fixture 근거를 재사용했다.

주 세션의 추가 시간차 재현에서는 지속 사용을 껐다가 곧바로 다시 켜거나, 폐기된 설정 기기를 다른 기기로 바꾸면 이전 확인이 여전히 실행 상태로 남는 결함을 발견했다. 진행 중 코드 검수를 중단하고 동일 변경에 수정을 포함했다. 두 경우를 먼저 실패하는 회귀로 확인한 뒤, 설정 변경 트랜잭션에서 현재 수시 확인의 대기·실행 상태를 취소하도록 했다. 재시작 뒤 취소 유지, 늦은 응답 사용량 보존 및 결과 거절을 확인했으며 수정 후 전체 907개 검사가 생략 없이 통과했다. 실제 모델의 정상 흐름은 바뀌지 않았으므로 앞선 6요청의 원문 근거는 실행 당시 커밋으로 보존하고 재실행으로 꾸미지 않았다.

## 같은 구독 대화에서 공개 자료 조사

현재 선택한 구독 모델의 공식 웹 검색을 직접 대화에 연결했다. 현재 사용자 요청과 최근 사용자 발화만 별도 조사 요청에 전달하며, 메일·파일 원문이나 모델이 제안한 검색어를 이 경로로 전달하지 않는다. 자동 확인에는 웹 도구를 추가하지 않았다. 사용량·취소·계정 경계와 대화 기록은 기존 서비스가 유지한다.

[첫 실제 대화 실행](../evals/assistant-v1/results/2026-10-09-public-research-first.json)은 두 회사 모두 조사 보고서 해석에 실패했다. 뒤이은 공개 자료 진단에서 URL 대신 공식 `oai-finance` 피드가 포함된 실제 응답을 확보해 같은 오류를 재현했다. 해당 공식 피드명을 보존하되 모르는 유형은 계속 거절하도록 수정했고, 저장한 동일 응답이 오프라인에서 정상 해석되는 것을 확인했다. 별도 금융 진단 한 번은 종료 코드 143으로 끝나 요청 1회의 사용량이 미확인으로 남았다. 그 결과를 성공 실행에 합치지 않았으며 해당 시점의 서비스 복구를 확인했다.

[수정 후 실제 대화](../evals/assistant-v1/results/2026-10-09-public-research.json)는 Microsoft·Costco 조사와 후속 요약에 11 observed / 0 unknown을 사용했다. 사용자 발화는 각각 “그 회사 투자할 만한지 알아봐.”와 “아까 이야기한 회사, 지금 검토할 가치가 있는지 근거를 찾아 판단해줘.”였다. 회사와 기준은 이전 합성 대화에서 찾았으며 자료 첨부·출처 목록·추가 사용자 준비 없이 실제 공개 자료를 조사했다. 후속 요청은 새 검색 없이 판단을 세 줄로 줄이는 것이었다. 거래·계좌 조회·다른 계정·API 과금 전환은 없었다.

[독립 검토](../evals/assistant-v1/results/2026-10-09-public-research-review.json)는 주요 공식 실적·회원 지표·기준 주가와 계산을 원문에 대조해 두 조사 답변의 내용·판단을 제한된 범위에서 통과로 판정했다. Microsoft 후속은 출처를 보존했다. Costco 후속은 문맥 정리 뒤 과거 결과를 읽었으나 원래 근거가 복원되지 않아, 내용은 맞아도 최종 요약에서 인용이 빠졌다. 이 결함은 통과로 숨기지 않고 아래 보충 실행에서 수정·재검증했다. 공급자 보고서 확인을 Tada 자체의 독립 웹페이지 재검증으로 표현하지 않는다.

이 환경에는 검색 가능한 과거 분석과 현실적인 무관한 후보가 부족해 정식 A01 수락으로 인정하지 않는다. 정식 사례 상태는 **5건 통과·11건 미실행**을 유지한다. 이번 수정 뒤 전체 Node 검사 926개가 생략 없이 통과했으며, 네이티브 코드·계약 생성물·의존성은 앞서 검증한 상태와 같아 Rust·프로세스 fixture 근거를 재사용했다. 데스크톱 1280px와 390px 브라우저에서 실제 조사 응답의 표·안전한 출처 링크·넘침 여부를 확인했으며 물리 휴대폰 전달 검증은 아니다.

후속 복원 수정은 명시적으로 읽은 같은 저널의 과거 조사 답변에서 원래 근거를 되살리며, 본문은 문맥 한도 안에서 제공한다. 위조 근거·현재 취소·좁은 문맥·재시작 회귀를 포함한다. [보충 실제 실행](../evals/assistant-v1/results/2026-10-09-public-research-recall.json)은 두 회사의 앞선 실제 응답을 합성 저널에 보존하고 최근 문맥을 비운 상황이다. 실제 모델이 이력 검색과 상세 읽기를 통해 온전한 답변과 원출처를 복원했고, 각각 3 observed / 0 unknown / 0 웹 시도로 세 줄 요약을 제공했다. [독립 감사](../evals/assistant-v1/results/2026-10-09-public-research-recall-review.json)도 두 변형의 의미와 출처 연속성을 통과로 판정했다. 자연 발생한 장기 압축 전체를 새로 검증한 것으로 확대하지 않는다. 실행 당시 구현은 `e15cb87`이며 앞선 정상 웹 실행 `935044b`와 구분한다.

독립 커밋 검수는 세 추가 결함을 합성 재현했다. 캐시된 같은 보고서의 다른 출처 번호가 다음 답변에서 거절됐고, 미완료·취소 스트림에 이미 포함된 사용량이 유실됐으며, 모델이 Markdown 링크를 생략하면 원출처 URL이 결과에 보존되지 않았다. 보고서 확인은 출처 번호와 분리하되 경로·해시·시각·인용 메타데이터는 일치해야 한다. 스트림 수집 실패에도 유효한 관측 사용량을 원장에 넘긴다. 검증된 URL·제목을 답변의 암호화된 근거에 선택적 필드로 보존하고, 복원 시 URL·형태를 검증하며, 브라우저 출처 목록에 안전한 링크를 표시한다. 과거에 URL 없이 저장된 근거는 읽을 수 있지만 없는 주소를 만들어 넣지 않는다. 수정 후 전체 Node 검사 **935개**가 생략 없이 통과했다. 새 근거 필드는 연락 서비스의 기존 JavaScript 내부 결과·체크포인트에만 적용하며 Rust wire 계약·생성물·의존성은 바꾸지 않았다.

## 브라우저 연결 복구

실제 대화에서 서버의 답변은 저장됐지만 브라우저가 처리 중 상태에 머물러 새로고침이 필요했다. 정확한 운영 장애 원인은 확정하지 않았으며 데스크톱 앱 종료의 원인으로 단정하지 않는다. 별도 계정·모델 없는 HTTP 재현에서는 첫 이벤트 연결을 204로 종료했을 때 기존 클라이언트가 상태를 한 번만 읽고 멈추는 것을 실제 Chromium에서 확인했다.

종료된 스트림을 다시 만들고, 이벤트 누락 시에도 상태를 주기적으로 읽도록 수정했다. 상태 요청 시간 제한, 실패 간격 증가, 오래된 응답·이벤트 무시, 인증 만료·로그아웃 시 중단을 같은 경로에 넣었다. 자동 복구는 메시지 POST를 실행하지 않으며 기존 접수 번호·작성 중 입력을 유지한다. 수정 후 동일 Chromium 재현에서 연결 두 번으로 복구했고 서버에서 완료한 결과가 새로고침 없이 표시됐다. 테스트 서버가 중단·재시작된 뒤에도 결과와 입력이 복구됐으며 HTTP 쓰기 횟수는 0이었다. 이는 로컬 브라우저·전송 계층 검증이며 물리 휴대폰이나 데스크톱 앱 충돌 복구 검증은 아니다.

독립 검수에서는 반복되는 SSE 오류가 이미 예약된 상태 조회를 계속 뒤로 미루는 문제를 재현했다. 더 이른 조회 시각은 유지하도록 수정했고, 상태 API만 먼저 복구된 경우에도 결과가 나타나는 회귀를 추가했다. 주 세션의 추가 검사에서 주기적 조회가 펼친 지난 업무 목록을 초기화하는 문제도 확인해, 업무 상태가 같으면 기존 표시를 유지하고 실제 변경이 있으면 갱신하도록 했다.

재검수는 첫 페이지 밖의 업무를 변경했을 때 같은 스냅샷 캐시가 예약·취소 상태 표시를 막는 회귀를 발견했다. 화면 유지 최적화를 주기적 상태 조회에만 적용하고, 사용자의 변경과 변경 이벤트에서는 캐시를 사용하지 않도록 제한했다. 여섯 번째 업무의 자동 확인 예약·재조회·취소까지 실제 클라이언트 코드로 회귀 검사했다.

후속 검수에서 변경이 적용된 뒤 응답·이벤트가 모두 유실되면 첫 페이지 비교만으로는 지난 업무 표시를 복구할 수 없음을 확인했다. 최종 구현은 인증된 상태 응답의 `followups.view_revision`을 사용한다. 이 표시는 현재 SQLite 연결의 변경 횟수와 호스트별 난수의 해시다. 대화·업무 변경과 호스트 재시작 때 바뀌며 읽기와 주기적 연결 신호에는 유지된다. 서비스 이벤트를 발생시키지 않는 타이머·복구 쓰기도 포함한다. 롤백된 쓰기는 보수적으로 화면을 무효화할 수 있다. 표시용 값일 뿐 업무 버전·실행 권한·저장 스키마를 바꾸지 않는다. 변경 요청 전에 화면 캐시도 무효화한다. 별도 중단 상태를 두어 로그아웃·기기 인증 해제 뒤 늦은 메시지 접수 응답이 복구 조회를 재개하지 못하게 했으며, 새 연결 성공만 이를 다시 열 수 있다. 실제 SQLite·HTTP로 첫 페이지 밖의 예약 변경, 표시값 안정성·재시작, 미연결 조회 거절을 확인했고 클라이언트에서는 응답 유실 뒤 취소 상태 재조회와 늦은 응답 차단을 확인했다.
