# 2026-10-07 개발 검증 기록

**출시 불가.** 이 작업의 목표는 시장에 내놓을 완성된 개인 비서이며, 아래는 그 과정에서 확인하고 고친 결함이다. 제품 평가 16건 중 A10/A15/A16을 각각 두 변형으로 실행했고 세 사례 모두 전체 기준을 통과하지 못했다. 나머지 13건은 미실행이다. 로컬 브랜치는 `codex/assistant-integration`, 기준점은 PR #16의 `4e9dbdcc28574544178a77099c803b8a698afab0`, 검토한 수정 커밋은 `4e8c85a`다. 원격 반영·병합·배포는 하지 않았다.

## 수정과 관측

- Rust 저장소를 닫아도 복제된 잠금 파일 디스크립터가 남으면 바로 다시 열지 못했다. 두 DB 연결을 닫은 뒤 잠금을 명시적으로 해제하도록 수정했다. 동일 회귀 검사는 기준점에서 `AlreadyOpen`으로 실패하고 수정본에서 통과했다. 원래 이슈 #14의 간헐적 CI 실패에 이 경로가 실제 원인이었는지는 입증하지 않았다.
- 도구 선택을 위해 모델이 선언한 추론 기능을 사용하고 전체 출력은 4,096토큰으로 제한했다. 비추론 모델의 768토큰 제한은 그대로다. 별도 추론 채널은 보관·출력하지 않으며 잘린 출력과 본문에 섞인 추론 표시는 여전히 거절한다.
- 잘못된 도구 인자를 재제안할 때 호스트 스키마의 누락 필드와 타입을 알려준다. 인자값이나 권한을 대신 채우지 않는다. 실제로 실행하지 않은 실패 호출과 채택하지 않은 답변 초안은 복구가 끝난 뒤 다음 대화에 반복하지 않는다. 원문 사용자 메시지, 실제 관측, 채택한 답변과 사용량은 보존한다.
- 출처를 읽지 않은 일반 대화에 가짜 인용이 붙으면 인용을 제거하도록 복구한다. 이전에는 존재하지 않는 인용을 다시 요구해 일반 대화도 실패했다. 고친 뒤 사전에 정한 3회 연속 연락/재시작 검사를 모두 통과했다.
- 예약 실행에는 현재 승인이 이미 유효하다는 호스트 상태를 전달한다. 과거의 승인 대기 제안을 현재 상태로 잘못 설명한 실제 응답이 수정의 근거다.

## 실행 근거와 한계

Linux/WSL, Node 24.21.0, Rust 1.98.1에서 `npm run check` **458개 통과**, Rust fmt/clippy/workspace/process-fixtures 검사를 통과했다. 저장소 집중 검사는 153개 통과했다. `npm ci --ignore-scripts --no-audit --no-fund`로 잠긴 의존성을 설치했다. 원본 설계 SHA-256은 기준점과 동일한 `adef0d1d29fd69bee443e5b2d91a9852252ac39fa3fff1af061d704464885e4b`이다.

설치된 Chrome 155.0.8059.39에서 연락 및 예약 재확인 브라우저 검사를 통과했다. 390/1280 너비의 독립 브라우저 문맥, 페이지 종료 후 처리, 재접속, 승인 수락·거절과 원문 비실행을 검사했다. 모델과 시각은 합성 fixture이며 실제 휴대폰, 원격 네트워크, Telegram 계정 시험은 아니다. 이전 관리형 브라우저의 정책 차단을 우회하지 않았다.

실제 모델은 격리된 loopback Ollama 0.32.13의 `qwen3:8b`를 사용했다. CI의 0.34.0과는 다른 런타임이다. 모델 지문·수정 과정의 성공과 실패·원본 보고서 해시는 [실행 기록](../evals/assistant-v1/results/2026-10-07-local-qualification.json)에 함께 보존한다. 실제 사용자 자료·계정·비밀값과 비공개 추론은 없다. 예약 시각만 일관된 Date fixture로 이동하며 SQLite, HTTP, 로컬 자료 게이트웨이, 파일 변경/재읽기와 재시작은 실제 실행이다.

초기 모델은 예약을 약속만 하고 저장 도구를 호출하지 않았다. 추론 활성화 후에는 인자 누락, 복구 대화 누적으로 인한 문맥 초과가 드러났다. 이를 고친 중간 버전은 기존 예약 검사 18개를 통과했지만 후속 답변의 출처 누락은 기존 검사가 잡지 못했다. 해당 검증을 추가한 뒤에는 **실패로 기록**한다. 일반 자료 탐색 검사에서도 후속 인용 누락을 관측했다. 성공 사례 하나로 모델을 출시 적합으로 판정하지 않는다.

최종 수정 커밋에서는 실제 8B 모델의 연락 검사 3회, 자료 탐색 2개 변형, 후속 인용 검사를 포함한 예약 검사 19개가 통과했다. 별도 GPT-6.1-sol/Max 코드 검토는 새 결함을 발견하지 못했고 필수 회귀 검사도 다시 통과했다. 선택한 처리 등급은 default이며 실제 적용 등급은 런타임 출력에 없어 별도로 검증하지 않았다.

그 뒤 추가한 한국어 [수용 검사](../evals/assistant-v1/contact-acceptance-candidate.mjs)는 실제 ContactService·암호화 DB·로컬 파일 게이트웨이를 사용한다. A10은 자료 속 지시, A15는 무관한 개인정보, A16은 관측 부재를 검사한다. [8B 실행 원문](../evals/assistant-v1/results/2026-10-07-acceptance-8b.json)과 [독립 의미 검토 및 주 세션 확인](../evals/assistant-v1/results/2026-10-07-acceptance-review.json)을 보존한다. 필요한 기계 검사를 통과한 것과 사례 통과를 구분했다. 6개 변형 중 A16의 첫 변형만 통과했고, 2개는 맥락을 설정하는 일반 대화 단계에서 실패했다. 허용 자료만 읽은 경우에도 불필요한 범위 확대 질문과 확인하지 않은 상태 추정이 남았다.

14B는 동일 장비에서 약 11.5 GiB의 GPU 메모리 사용을 관측했지만 전체 최대치 측정은 아니다. [비교 기록](../evals/assistant-v1/results/2026-10-07-acceptance-14b-partial.json)은 첫 2개 변형까지만 실행했다. 사용자가 기존 구독 우선 방향을 명확히 하면서 이 비교를 중단했다. 남은 4개를 성공으로 간주하거나 14B를 채택하지 않았다. 격리된 테스트 서버와 모델 실행은 종료했다.

## 이어서 할 일 — 사용자가 기본 경로를 결정함

기존 구독의 **공식 연결을 기본 경로**, API와 로컬 모델을 선택 가능한 대안으로 제공한다. 상용 제품 품질을 8B 로컬 CI에 맞추지 않는다. 다음 구현은 같은 비서의 대화·도구·사용량·취소 경로에 Sign in with ChatGPT를 연결하는 일이다. 아직 실제 계정을 연결하지 않았다. 사용자가 다시 이 기본 선택을 승인할 필요는 없다.

[공식 문서](https://developers.openai.com/siwc/token-sharing-open-source)에 따르면 공개된 ChatGPT plan usage 경로는 오픈소스·로컬 앱을 대상으로 하며 유료/원격 호스팅 앱은 별도 접근 절차가 있다. 현재 Tada의 오픈소스 로컬 앱 형태에서 공식 OAuth를 구현하되, 유료 중앙 서비스 운영 자격과 혼동하지 않는다. 공식 DevKit의 라이선스는 비상업용이고 npm 패키지도 공개 배포되어 있지 않으므로 그대로 가져오지 않는다. 공개된 프로토콜을 독립 구현하고 기존 앱의 토큰을 재사용하지 않는다.

출시에는 일반 작업의 실제 실행과 결과 확인, 설치/초기 설정, 장기 기억과 명시적 예산 갱신, 상시 연락 운영, 실제 계정/기기, 지원 플랫폼과 제품 평가가 남았다. 64회 기록 수명과 14 KiB 문맥 제한은 그대로이며 장기 비서의 완성된 기억이 아니다. 구현·검증 가능한 범위와 외부 연결·비용·배포 승인을 구분한다.


## 2026-10-09 — 연결된 Google 계정에서 문서 완성

이 절은 위의 로컬 모델 실험과 별개인, 기존 ChatGPT 구독을 이용한 제한된 실제 실행 기록이다. 제품 전체 합격이나 공개 배포 승인이 아니다.

- 사용자 발화: “최근 메일과 앞으로 일주일 일정을 보고, 내가 먼저 챙길 일만 우선순위대로 정리해서 문서로 만들어줘.”
- 사전 권한: 소유자가 지정한 Google 계정의 Gmail·기본 캘린더 읽기와, 필요한 발췌를 현재 선택한 ChatGPT 구독 계정으로 전송하는 것을 승인했다. 모델·계정·결제 경로를 바꾸지 않았다. 시험은 두 사용자 턴, 합계 최대 8회 모델 요청, 턴당 120초로 제한했다.
- 첫 턴: 모델 요청 3회 뒤 기존 14,000바이트 문맥 제한으로 실패했다. 실패 기록을 보존했고 완성 문서로 인정하지 않았다. 원래 실패의 일시적 도구 내용은 저장되지 않아 정확한 바이트 구성을 사후 특정하지 않았다.
- 수정: 실제 직렬화·SSE 회귀로 누적된 암호화 연속성 정보가 작은 요청 한도를 넘는 경로를 확인했다. 구독 공급자의 전체 요청 한도를 64 KiB로 명시하고 추론·도구 결과 승인에 동일하게 적용했다. 자료·문서 크기, 접근 권한, 호출 횟수와 저널 형식은 유지했다. 코드 `7421095`의 전체 Node 검사 753개와 네이티브 읽기 broker 검사가 통과했고, 독립 커밋 검토에서도 수정할 결함이 없었다. 독립 검토의 Rust 형식·Clippy·워크스페이스·process-fixture 검사도 통과했다.
- 재실행: 같은 발화에서 모델이 메일·일정·저장된 일을 조회하고, 관련 메일 본문 읽기와 문서 준비를 선택했다. 4회 모델 요청으로 약 55초에 「이번 주 먼저 챙길 일」 버전 1을 저장했다. 마지막 두 요청은 각각 15,332 / 17,500바이트로 이전 한도를 넘었지만 새 한도 안에서 완료됐다. 인용한 출처 3개를 다시 읽어 검증한 뒤 답변을 채택했다. 발송·일정 변경·납부·알림 등록은 하지 않았다.
- 보존: 실제 서버를 정상 설정으로 재시작한 뒤 같은 Google 연결, 이전 실패 기록, 저장 문서와 내려받기 링크를 브라우저에서 확인했다. 임시 시험 호출 제한은 정상 실행 프로세스에 남기지 않았다.

두 턴의 실제 모델 요청은 총 7회였으며 모두 사용량이 확인됐다. 입력 17,166토큰·출력 1,222토큰은 실패한 첫 턴을 포함한다. 원문 이메일·계정 식별자·자격 증명은 이 검증 기록에 싣지 않는다.

중요한 한계: 메일 목록은 자료 한도 때문에 2건으로 축약됐고, 한 메일 본문은 일부만 읽었으며 다른 본문 요청은 한도 오류를 반환했다. 따라서 전체 받은편지함을 빠짐없이 살폈거나 답장 여부를 확인했다고 주장하지 않는다. 기본 캘린더 결과 2건은 잘리지 않았다. 문서도 이 한계와 사실·제안을 구분했다. 후속 문서 수정은 이번 실제 실행 예산 안에서 수행하지 않았고, 합성 회귀 근거만 있다. 먼저 챙겨보기의 실제 제안 품질, 휴대폰 송수신, 상시 운영, 플랫폼별 설치와 전체 제품 평가·공개 배포 요건은 별도 검증이 남아 있다.
