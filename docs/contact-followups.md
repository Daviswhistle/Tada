# 같은 비서가 맡긴 일을 기억하고 다시 연락하기

**2026-10-07 후속 변경:** 최신 연락 실행 파일과 DB v4 전환은 [일회성 로컬 재확인](contact-reviews.md)을 따른다. 이 문서의 v3 구현·시험 기록은 역사적 범위로 보존한다. 단순 알림은 여전히 모델을 호출하지 않는다. 재확인은 별도 소유자 승인으로만 활성화한다.

2026-10-05 · 브라우저/Telegram 연락 호스트의 후속 구현. 실행 가능한 코드와 로컬 회귀 검증이며, **실제 모델·Telegram 계정·휴대폰 검증과 배포는 아직 아니다.** 기존 두 연락 패키지와 마찬가지로 GitHub에 업로드되지 않은 소스 변경분이다.

## 사용자 경험

사용자가 평소처럼 일을 이야기하면, 기존 대화 모델이 필요한 경우 현재 맡긴 일을 조회하고 새 기록 또는 변경을 제안한다. 사용자가 별도로 할 일 양식을 채우거나 파일·업무 ID를 준비할 필요는 없다. 한 번 확인한 기록은 대화 창이 닫혀도 남고, 다른 기기나 재시작 뒤 같은 비서에게 “맡겨둔 일 뭐가 남았어?”라고 물어볼 수 있다.

기록에는 제목, 내용, 상태, 기다리는 대상, 선택적인 확인 시각이 있다. 지금 상태는 **챙길 일 / 회신·조건 대기 / 사용자 확인 완료 / 취소**다. 기존 일을 바꾸면 새 버전을 만들고 이전에 승인한 제안·알림을 다시 활성화하지 않는다. 과거 제안과 대화는 별도로 보존한다.

이번 버전에서는 새 등록·변경 시 **내용과 시각을 한 번 확정**해야 한다. 브라우저의 `이대로 맡기기` 또는 Telegram의 `/confirm PROPOSAL_ID`를 사용한다. 모델이 “기억했다”고 말하는 것만으로 알림을 만들지 않는다. 확인 카드는 정확한 현재 사용자 인용과 해석된 날짜/시간대, 기다리는 조건을 보여준다. 조회에는 새 확인이 필요 없다. 이 확인 단계는 현재 구현의 제한이며, 모든 분명한 위임을 사람 비서처럼 즉시 수행하는 수준을 완료했다고 주장하지 않는다.

모델 도구는 `list_followups`와 `propose_followup` 두 개를 기존 자료 읽기 도구와 함께 받는다. 같은 일반 추론/도구 루프가 사용자의 표현을 해석한다. 특정 한국어 문구를 정규식으로 분기해 업무를 만드는 방식이 아니다. `/confirm`, `/dismiss`, `/cancel`, `/stop`은 자연어 해석이 아니라 명시적인 연락 제어다.

## 실제로 챙기는 범위

확정한 시각이 되면 호스트는 업무에 연결된 **일회성 확인 알림**을 저장하고 기존 연락 대기열로 전달한다. 이 동작에는 모델을 다시 부르지 않는다. 호스트가 늦게 실행되면 누락분을 한 번 처리하며, 5분 이상 늦은 확인은 늦었다고 표시한다. 같은 시각을 재조회하거나 재시작해도 동일 버전의 알림을 새로 만들지 않는다.

`회신·조건 대기`는 **무엇을 기다리고 있는지 기록**하는 기능이다. 메일·메신저에서 그 사람의 실제 답장을 조회하지 않는다. 알림이 울린 것을 회신 확인 또는 맡긴 업무 전체 완료로 표시하지 않는다. 시간 없이 기록한 업무는 저장·조회되지만 자동으로 반복 관찰하지 않는다.

`사용자 확인 완료`는 소유자가 완료 상태를 확정했다는 기록이다. 외부 시스템 영수증이나 독립적인 결과 검증으로 만들어진 task 성공과 구분하며, `completion_basis=owner_confirmation`을 유지한다. 일반 메일 발송, 일정 수정, 임의 셸, 파일 변경과 조건 충족 후 자동 재실행은 이 기능에 없다.

## 브라우저와 Telegram에서의 전달

브라우저에는 같은 업무 목록, 미확정 제안, 확인할 알림이 보인다. `확인했어요`는 알림을 읽었다는 처리이며 업무를 완료 상태로 바꾸지 않는다. 업무의 변경·취소·완료는 대화로 제안하고 정확한 새 내용을 확인한다. 이전 기록은 페이징해 조회할 수 있다.

Telegram으로 맡기고 그 채팅에서 확정한 업무는 승인된 제목·대기 조건으로 알린다. 브라우저에서 확정한 업무는 Telegram에 **본문 없는 확인 알림**만 보낸다. Telegram에서 그 업무를 다시 질문하면 기존 연결 동의 범위 내에서 답변에 내용이 포함될 수 있다. 최초부터 채널별 개인정보 경계를 유지한다.

`/dismiss PROPOSAL_ID`는 아직 확정하지 않은 제안을 버린다. `/cancel`은 기존처럼 최근 대기·실행 중인 **답변 요청**을 취소하며, 이미 확정한 모든 업무를 취소하지 않는다. `/stop`은 해당 Telegram 연결을 해제한다.

## 실행 및 기존 연락 DB 전환

전체 Tada 기준 체크아웃에 누적 패치를 적용한 뒤 기존 도구/의존성 준비를 따른다. 실제 설치한 로컬 Ollama 모델을 명시하고, 필요할 때만 이미 준비한 본인 봇을 연결한다. 아래 플레이스홀더는 실제 모델 ID로 바꾼다. 이 패키지는 모델·봇·VPN·서버를 설치하거나 계정을 생성하지 않는다.

```sh
npm ci --ignore-scripts
npm run contact -- --help
# 새 연락 기록일 때만 --init
npm run contact -- --data ./tada-contact-private --init --model YOUR_INSTALLED_LOCAL_MODEL --timezone Asia/Seoul --telegram
```

기존 연락 기록을 사용하는 경우, **초기화 대신 명시적 전환**을 한다. 기존 암호·모델·자료 범위를 유지한다.

```sh
npm run contact -- --data ./tada-contact-private --model YOUR_INSTALLED_LOCAL_MODEL --timezone Asia/Seoul --upgrade-contact --telegram
# 이후 정상 재시작: --init, --upgrade-contact 모두 제외
npm run contact -- --data ./tada-contact-private --model YOUR_INSTALLED_LOCAL_MODEL --timezone Asia/Seoul --telegram
```

새 연락 실행 파일은 **연락 DB v3**를 사용한다. v1은 메시징용 v2를 거친 뒤 v3로, v2는 v3로 전환한다. 각 전환 전에 새 파일로 일관된 SQLite 백업을 만들고 동기화하며, 테이블·버전·식별값 변경을 하나의 트랜잭션으로 기록한다. 이전 저장소를 일반 시작으로 몰래 전환하지 않는다. 처리 중인 요청 또는 보내는 중인 메시지가 있으면 전환을 막는다. 이 v3는 기존 Rust 작업 DB의 v3와 별개다.

암호와 봇 토큰은 실행 중 호스트 터미널에서 숨김 입력한다. 브라우저 접속은 기존과 같이 기본 loopback이며, 사설 HTTPS/VPN은 별도 운영 설정이다. Telegram은 선택적으로 켜며 기존 전용 봇 승인/연결 경로를 그대로 사용한다. 실제 실행 호스트가 켜져 있어야 알림을 보낼 수 있다.

## 날짜, 권한과 명확한 한도

모델에는 현재 호스트 UTC 시각과 선택한 IANA 시간대를 제공한다. 실행 시각은 초와 UTC offset이 있는 한 번의 timestamp로 고정한다. 모호한 현지 문자열, 불가능한 날짜, 이미 지난 시각을 임의 보정하지 않는다. 표시 시간대 변경이 이미 승인한 timestamp를 이동시키지 않는다. 반복 일정·서머타임 반복 occurrence·자유 형식 날짜의 독립적 의미 검증은 구현하지 않았다.

알림은 확정 기기의 남은 접근권 수명 안에 있어야 한다. 기기 수명은 기존처럼 최대 30일이며, 그보다 뒤의 시각은 `CONTACT_FOLLOWUP_DEVICE_EXPIRES`로 거절한다. 새 연결을 기존 알림에 자동 승계하지 않는다. 기기가 해제·만료되면 그 기기가 확정한 업무의 새 알림은 중지하지만 기록 자체는 남긴다. 다른 유효 기기에서 현재 내용을 수정·다시 확정할 수 있다. 화면과 조회 결과에 알림 중지 상태를 표시한다.

작업 기록 최대 1,000개, 제안 이력 최대 1,000개, 미확정 제안 최대 32개, 모델 응답당 제안 최대 4개다. 업무 목록은 한 페이지 5개와 명시적 다음 cursor를 제공한다. 모델이 과도하게 긴 기록을 한 대화에 읽으면 기존 14 KiB 문맥 한도에서 중지할 수 있다. 기존의 journal당 모델 요청 64회, 대기 16개, 대화 turn 1,000개 제한은 바뀌지 않았다. 재시작·알림으로 그 한도를 다시 채우지 않는다. 장기 비서에 충분한 기억 관리나 무제한 사용을 제공하는 단계는 아니다.

## 저장, 취소와 불확실성

제안은 모델 실행 중에는 메모리에만 둔다. 지원되는 전체 도구 요청 묶음을 검사하고, 최종 답변과 복원 체크포인트를 커밋하는 트랜잭션에서 함께 저장한다. 취소나 제안 저장 실패 뒤 “저장해두었다”는 결과가 혼자 남지 않는다.

확정 요청에는 원래 제안 ID만 보낸다. 서버는 현재 기기 권한, 제안 만료(24시간), 원래 사용자 메시지, 정확한 고정 내용, 해당 업무의 현재 버전을 다시 검사한다. 동시에 들어온 변경은 version CAS로 구분한다. 과거 확인을 재전송해도 새 버전을 되돌리거나 취소한 일을 살리지 않는다. 기존 다른 버전의 제안은 대체된 상태로 남긴다.

후속 알림과 Telegram 송신 대기열은 함께 커밋한다. 변경/취소/읽음/접근권 해제는 **아직 보내기 전**의 이전 알림을 억제한다. 이미 보내는 중이거나 보낸 메시지는 취소했다고 회수된 것으로 표시하지 않는다. 429로 재시도 가능해진 메시지도 다음 전송 직전에 최신 업무 버전·알림 상태·권한을 다시 확인한다. 응답 손실이나 호스트 종료의 미확정 전송은 자동 재발송하지 않는다.

업무의 제목·내용·인용·대기 대상, 제안과 알림 본문은 기존 AES-GCM 암호화 저장을 재사용한다. ID·상태·확인 시각 등 메타데이터는 평문으로 남는다. 같은 OS 사용자/관리자 또는 DB 전체 백업 동시 롤백에 대한 완전한 방어를 약속하지 않는다. 이전 DB를 임의로 덮어 복원해 발송 이력을 지우면 안전한 자동 복구가 보장되지 않는다. 이 패키지는 복원 마법사나 독립 보안 감사 결과가 아니다.

## 이번 실행 검증

Linux / Node **22.16.0** / TypeScript **5.8.3**의 격리된 소스 변경분 환경에서 다음 검사를 수행했다.

```sh
node --experimental-strip-types --test packages/engine/tests/contact.test.mjs packages/engine/tests/telegram-contact.test.mjs packages/engine/tests/followups.test.mjs
```

기존 50개와 신규 30개, **80개 함수가 통과**했다. SQLite, Node HTTP 서버/클라이언트, 실제 자식 프로세스 강제 종료를 사용했다. 신규 통합 시험은 제품의 Telegram 직렬화/수신/전송 경로로 일반 요청을 받고, 제안을 확정하고, 호스트를 다시 열고, 다른 PC 클라이언트에서 같은 업무를 읽고, 확인 시각 알림을 정확히 한 번 전송했다. 같은 흐름에서 알림 자체의 모델 요청은 0회였다.

**모델과 Telegram의 외부 서비스 응답은 모의 응답이다.** 이 테스트가 자연어 이해 품질, 실제 Telegram 수락/폰 표시, Windows, 실제 모바일 브라우저 또는 인터넷 배포를 입증하지 않는다. 실행 파일 시험도 제품 CLI 코드를 쓰되 로컬 추론 어댑터·TTY·Telegram upstream을 모의 구성했다.

제안 저장·확정·알림 저장 후의 세 경계에서 실제 자식 프로세스를 종료했다. 기존 메시징 시험의 네 전송 경계와 잘못된 외부 API 응답 시험은 유지했다. 초기 신규 테스트에서 발견한 재요청 응답 필드 불일치와 시험 API의 close/dispose 계약을 수정했다. 추가 리뷰에서 429 후 재큐잉된 오래된 알림과, 실제 CLI의 이전 v2 전용 검사도 고쳤으며 각각 회귀 검사로 고정했다. 테스트/오류 종류/제한 시간을 제거해서 통과시키지 않았다.

생성된 패키지의 `validation.json`과 로그가 명령별 환경·결과의 기준이다. 전체 저장소의 Node/Rust CI, 실제 모델을 통한 새 후속 업무, 실제 봇/휴대폰, 원격 배포, 광범위 비서 평가16건은 **미실행**이다. 원문 설계와 기존 Rust/wire/lockfile은 변경하지 않는다.

공식 API 참고: [Node SQLite](https://nodejs.org/api/sqlite.html), [Telegram Bot API](https://core.telegram.org/bots/api). 확인일 2026-10-05. 공식 문서의 API 동작은 이 코드의 실제 서비스·보안 검증을 대신하지 않는다.
