# Tada 제품 계약 — 사람에게 맡기듯 위임하기

상태: 사용자의 2026-10-04 수정 요구를 반영한 **현재 제품 요구사항**. 아래 동작은 구현 완료 선언이 아니다. 현재 구현과 실행 증거는 README와 각 PR에 따로 기록한다.

## 1. 바로잡은 목표

Tada는 사용자가 자료, 경로, 원인, 절차를 준비해서 조작하는 작업 실행기가 아니라, **일상적인 말과 허용된 맥락으로 필요한 일을 파악하고, 자료와 대상을 찾아, 실행과 확인까지 맡는 개인 AI 비서**다. 사용자가 업무를 명세하는 수고도 위임 범위에 포함된다. 특정 문구마다 사람이 작성한 시나리오를 선택하는 제품으로 축소하지 않는다.

이번 변경의 직접 근거는 사용자의 다음 요구다.

> 자료를 지정하지 않아도 알아서 수집하고 찾아내고, 이 프로젝트 실행 오류를 고쳐줘가 아니라 이거 안 돼라고만 해도 알아서 알아듣고 작업해야 하고, 그냥 실제 사람 비서에게 하듯이 대할 수 있어야 해

### 문서의 우선순위와 변경 범위

이 요구는 기존 구현 계획을 **수정하는 새 요구**다. [2026-09-30 원문](design/source-2026-09-30.md)은 변경하지 않는다. 원문 §3.5의 질문 전 맥락 확인, §4.1의 첨부 없는 자연어 시작, §20의 기억은 관련 기반이다. 다만 그 문장이 아래의 모든 새 요구를 이미 상세히 규정했다고 주장하지 않는다.

현재 제품 동작과 개발 우선순위는 이 문서와 [현재 로드맵](roadmap.md)을 따른다. 과거 PR의 “다음 단계”, 원문의 폴더 중심 예시와 직렬 구현 순서는 이에 맞게 해석한다. 기존의 취소, 원본 보호, 권한, 개인정보, 외부 효과 확인, 완료 증거는 유지한다. 이 문서는 실행 권한을 발급하지 않으며 기존 wire/schema를 몰래 변경하지도 않는다.

## 2. 사용자에게 요구할 일과 비서가 맡을 일

사용자는 자연어로 말한다. 파일 첨부, 프로젝트 선택, 오류 로그, 검색어, 도구 이름, 저장 경로, 완성된 `TaskContract`는 시작의 필수 입력이 아니다. 연결과 관측 권한은 설정 또는 필요한 시점의 좁은 동의로 확보하고, 그 설정을 매 요청마다 반복하지 않는다.

비서는 요청에 필요한 만큼 기존 대화, 진행 중인 업무, 앞서 만든 결과, 확인된 선호, 허용된 현재 앱·화면과 연결된 자료를 찾는다. 무엇을 알아야 하는지 정하고, 관련 출처를 검색·수집·대조하며, 필요한 실행 수단을 선택한다. 조사로 알아낼 수 있는 사실을 질문 목록으로 사용자에게 돌려보내지 않는다.

이 관찰·탐색은 모든 대화 앞에 강제되는 긴 절차가 아니다. 단순한 답변에는 바로 답하고, 복잡한 위임에는 필요한 조사를 늘린다. 사용자의 의미를 이미 알면 대상을 다시 묻지 않는다. 모르면 아는 척하지 않는다.

| 요구 ID | 제품이 보여야 하는 동작 |
| --- | --- |
| AC-01 | 자료를 첨부하지 않은 요청도 접수하고 필요한 자료를 스스로 찾는다. |
| AC-02 | “이거”, “그 회사”, “아까 것”의 대상을 대화·현재 관측·업무 이력으로 식별한다. |
| AC-03 | 기억과 현재 상태가 다르면 관련 사실을 재확인하고 출처·시점을 구분한다. |
| AC-04 | 입력과 완료 조건을 조사하면서 구체화하되 사용자의 목적을 축소하거나 바꾸지 않는다. |
| AC-05 | 연결된 기능을 선택·조합하고, 없는 기능은 가용한 허용 경로 또는 필요한 연결로 해결한다. |
| AC-06 | 스스로 알아낼 사실은 조사하고, 진짜 선택·권한·해소되지 않은 중요한 모호성만 좁혀 묻는다. |
| AC-07 | 실제 사용자 목적이 달성됐는지 확인하고 결과·변경·필요한 다음 행동을 전달한다. |
| AC-08 | 후속 대화와 재시작에서 업무·결과의 관계, 사용자 수정, 취소와 실행 증거를 이어간다. |
| AC-09 | 관련성·동의·목적 범위 안에서 관측하고, 외부 내용이나 추정을 승인으로 승격하지 않는다. |

## 3. 동작 예시 — 문구별 실행 템플릿이 아님

**“그 회사 투자할 만한지 알아봐.”** 대화에서 회사와 사용자의 판단 기준을 찾고, 확인 가능한 공개 자료와 허용된 기존 자료를 스스로 수집한다. 회사가 명확하면 업로드를 요구하지 않는다. 이름이 같은 회사가 남으면 후보와 차이를 좁혀 묻는다. 회사명·파일명·출처 주소가 달라져도 같은 능력으로 처리해야 한다.

**“이거 안 돼.”** 허용된 활성 앱·화면과 직전 시도를 확인해 사용자가 하려던 일을 파악한다. 업로드 오류라면 업로드를, 파일이 열리지 않으면 파일 열기를, 실행 환경 문제라면 그 실행 경로를 조사한다. 곧바로 코드 프로젝트로 단정하거나 모든 사용자에게 경로·로그·재현 절차를 요구하지 않는다. 수정 뒤에는 사용자가 하려던 행동을 다시 확인한다. 화면 권한이 없으면 있다고 꾸미지 않는다.

**“아까 것, 너무 복잡해. 좀 고쳐봐.”** 앞선 결과와 사용자의 반응을 찾아 수정 범위를 파악하고, 기존 결과를 보존하면서 새 버전을 만든다. 최신 사용자 편집을 다시 확인한다. 검색 성공이나 새 파일 존재만으로 수정이 완료됐다고 말하지 않는다.

**“내일 미팅 준비 좀 해줘.”** 허용된 일정과 관련 대화를 찾아 어떤 미팅인지 파악하고, 필요한 자료와 준비사항을 정리한다. 자료 준비 위임을 일정 변경·초대 발송·새 구독 결제로 확대하지 않는다. 코딩과 보고서에 국한되지 않는 동일한 비서의 사례다.

## 4. 대화·관측·발견이 실행의 일부다

기본 흐름은 **말을 접수 → 필요한 맥락과 대상을 찾기 → 부족한 사실을 조사 → 업무 구체화와 실행 → 실제 결과 확인 → 후속 대화로 연결**이다. 관찰과 실행은 필요에 따라 반복하며 고정 단계 수를 갖지 않는다.

### 대화와 업무의 연속성

대화 ID와 메시지, 관련 task/run, 결과 버전의 연결을 보존한다. 한 대화가 반드시 한 작업은 아니고, 후속 대화가 반드시 새 작업도 아니다. 사용자가 대상을 수정하면 근거를 갱신하고 영향을 받는 계획과 아직 실행하지 않은 동작을 다시 검토한다. 이전 대상을 조용히 계속 사용하지 않는다.

기억에는 출처·관측 시점·유효 범위·수정 관계를 유지한다. 사용자 명시 선호, 직접 관측, 문서에서 추출한 사실, 모델의 가설을 구분한다. 가설은 사용자 선호나 실제 실행 사실로 저장하지 않는다. 삭제·수정한 기억을 오래된 요약으로 복원하지 않는다. 권한은 기억과 별도로 현재 승인 저장소에서 확인한다.

### 능동적인 자료와 도구 탐색

사용자가 어떤 파일이나 서비스를 지정하지 않았어도 비서가 관련 소스를 찾는다. 연결된 계정과 허용된 로컬 영역, 공개 자료 중 필요한 경로를 선택하고 부족하면 검색 범위를 갱신한다. 전체 홈 폴더·메일함·클립보드를 무조건 수집하는 방식은 쓰지 않는다. 관련성 없는 민감정보를 원격 모델로 보내지 않는다.

UI가 허용된 현재 관측을 제공하거나 엔진이 중개기를 통해 요청할 수 있어야 한다. 항상 켜진 화면·오디오 기록은 전제가 아니다. 요청 시 관측으로 충분하면 그 방식부터 구현한다. 관측이 만료됐거나 창·계정·문서가 바뀌면 다시 확인하고, 오래된 좌표나 핸들을 재사용하지 않는다.

필요한 자료나 기능이 없으면 대체 가능한 허용 경로를 찾는다. 새로운 계정 연결·확장 설치·권한 확대가 필요하면 그 목적과 범위만 묻는다. 전체 제어는 정식 지원 목표로 유지하지만, 넓은 위임이 사용자 의도를 추정해 지출·전송·영구 삭제를 승인하는 근거는 아니다.

## 5. TaskContract는 사용자가 채우는 양식이 아니다

**자연어 접수와 실행 계약을 분리한다.** 원문 메시지와 현재 연결 관계를 먼저 접수할 수 있어야 한다. 대상·출력 형식·출처가 미정인 상태는 곧바로 오류가 아니라 조사해야 할 업무 상태다. 접수에 허위 입력 경로나 가짜 완료 조건을 채워 기존 해시 시험을 통과시키지 않는다.

비서는 기존 허용 범위와 예산 안에서 조사하고, 증거가 생기면 대상·입력·계획·완료 조건을 점진적으로 구체화한다. “사용자가 첨부하지 않은 자료를 발견한다”는 것은 목적을 확장하는 일이 아니다. 다만 그 자료를 읽거나 외부로 전송할 권한이 생겼다는 뜻도 아니다.

실제 변경 전에 해당 동작의 대상 identity, 변경 범위, 최신 전제와 필요한 승인은 구체적이어야 한다. 내부 계약을 갱신할 때는 원문 지시와 이전 버전의 연결, 변경 근거를 남기고 영향을 받는 grant를 재검증한다. 이미 확정된 계약 hash를 덮어쓰거나 기존 wire의 검사를 느슨하게 하지 않는다. 필요한 버전 변경은 실제 대화 접수 경로와 함께 구현한다.

## 6. 질문과 자율성의 기준

질문 전에 관련 대화·결과·기억과 가능한 관측을 확인한다. 질문의 사유는 사실을 아직 검색하지 않았기 때문인지, 접근할 권한이 없기 때문인지, 사용자가 결정해야 하기 때문인지 구분한다.

맥락이 충분하면 바로 처리한다. 관련 조사를 해도 중요한 후보 둘이 남으면 “어떤 프로젝트인가요?” 대신 확인한 후보를 제시해 한 가지 선택을 묻는다. 관측이 전혀 없으면 그 한계를 밝히고 대상을 특정하는 최소 질문을 한다. 불필요한 질문 0개와 무근거 추측 0개를 함께 평가한다.

이미 승인된 범위에서는 반복 확인하지 않는다. 새로운 금전적 약정, 불명확한 수신자·공개 범위, 큰 영구 삭제, 권한 확대 등은 사용자 선택을 남긴다. 지연·로그인 필요·완료 불가를 숨기지 않고 다음에 필요한 행동을 말한다. 질문을 줄이기 위해 중대한 선택을 대신 정하지 않는다. 맡은 일의 선행 조사는 자율적으로 하되 별도 요청 없는 상시 감시나 반복 작업은 추가하지 않는다.

## 7. 성공 기준과 개발 변경

첫 사용자 검증은 자료와 정확한 경로가 없는 요청, 현재 환경에 따라 뜻이 바뀌는 요청, 며칠 뒤의 후속 요청으로 한다. 한 폴더를 지정해 계약 hash를 읽는 데모는 부품 시험으로 남긴다.

[비서 평가군](../evals/assistant-v1/README.md)은 대상 식별, 자율 수집, 최신성, 불필요한 질문과 사용자 준비 수고, 목적 달성, 후속 연결, 권한·개인정보를 함께 본다. 같은 문구에 다른 환경을 주고, 새 문구·파일명·앱 상태도 바꾸어 문구 매칭을 배제한다. 실제 모델과 실제 관측·실행 경로의 증거 없이 제품 통과를 기록하지 않는다. 현재 기준점은 **제품 평가 미실행**이다.

기존 실행 코어를 재사용하되 이제 작업 순서는 사용자 경험 단위로 정한다. 자연어 대화 접수, 필요한 맥락 조회, 실제 제공자 연결, 범용 읽기·수집·수정, 결과 확인, 후속 대화를 한 실행 경로에서 연결한다. 제공자 인증과 현재 환경 관측을 다시 마지막으로 미루지 않는다. 넓은 배포·확장 기능은 이후에 진행하되, 이 경로에 필요한 취소·권한·내구성 검사는 함께 유지한다.

문서·평가 정의를 바꾼 PR과 실행 기능을 만든 PR을 구분한다. 테스트 수·계층 수·PR 수를 비서의 완성도로 보고하지 않는다. 다음 기능 PR에는 사용자가 어떤 말로 시작했고 무엇을 준비하지 않아도 됐으며 실제 무엇이 해결됐는지 증거를 남긴다.
