# Owner control over local records

The normal app provides **Settings → My records → Delete records and connections**. The page explains the irreversible local scope and requires the owner's checkbox plus confirmation. A paired conversation device receives only a public setup URL; it cannot obtain the local setup capability or authorize deletion. Advanced custom-profile, manual-password and CLI Telegram launches do not expose this control.

The confirmed scope is this app's continuing conversation and its default ChatGPT/local-key profiles: conversations, documents, work, reminder/outbox state, connected-account secrets, historical recovery groups, migration copies, restored originals, canceled generations and partial recovery candidates. The app stops its current runtime and channels, checks that cleanup succeeded, and disables its own configured future startup before removing records. A failure in those steps stops deletion. It does not call a provider or revoke a remote grant.

Downloaded backup files, other Tada storage locations, unrelated user files, provider-side data/grants, browser copies, OS caches and completed external effects are outside this operation. Unlinking local files is not a physical secure-erasure claim. An independent backup can still restore its historical contents if its protection key or recovery code remains available. Individual-message forgetting is not implemented by this all-records operation.

## Durable deletion and restart

`AppPrivacy` operates only while the existing stable app owner lease remains held. It persists a private erase intent before stopping the runtime. Any pending/done erase state blocks ordinary automatic startup, restore and retry. On restart, the owner sees the pending operation and explicitly continues it; no old model request, reminder or message is revived.

The coordinator validates bounded, known storage-tree shapes, private ownership, single-link regular files and non-symlink parents, with a narrow exception for the validated same-directory Google configuration publication pair. Unknown files stop the operation. Every extant SQLite owner is checked; on POSIX its lease stays held through quarantine and removal, while native Windows checks the owner and relies on open-handle rename exclusion at dispatch. The coordinator records an exact private manifest, moves the known roots to a private erasure directory, and publishes exclusive file guards at the former conversation/key/profile paths. Old default launchers cannot reopen or initialize those guarded paths. Transient lease journals are ownership-checked but excluded from durable byte fingerprints.

All remaining quarantine contents are checked against the manifest before file-by-file removal, with a byte check again before each non-transient file is unlinked. No recursive force removal is used. Modified or unexpected remaining files halt further deletion. Partial guards, two-link publication, partial removal and interrupted final cleanup have resumable states. Records and connections remain stopped if cleanup is uncertain; a clean application restart is required.

Completion leaves a small non-secret tombstone and path guards. **Start fresh** is a separate owner action, itself resumable if interrupted; only then are the guards removed, the empty recovery directory recreated, and ordinary new-account setup allowed. A durable new-start intent permits this initialization even in the already-running background host and survives interrupted onboarding. It is cleared only when the new journal is open and the host is ready; ordinary missing-data background starts remain prohibited. Backup restoration becomes available again after this initial setup completes. The setup capability/lease remains application control metadata, not a saved provider connection.

The new UI state and private erase manifest belong to the Node app coordinator. Existing Rust execution contracts, journal schemas, historical receipts and provider credential formats are unchanged.

## Verification scope

Tests use temporary synthetic records/accounts only. They exercise current/original/canceled/partial record generations, real SQLite ownership, manifest/path tampering, unknown files, symlinks, fault boundaries, actual child-process termination, shutdown ordering, background disable, owner capability admission, transport ambiguity and explicit fresh startup. Browser checks cover the confirmation, completion and new-connection views, with no horizontal overflow at 320 and 390 CSS pixels. The visual fixture changes state only; it contains no records or accounts. Actual filesystem removal is checked separately through the coordinator and HTTP lifecycle tests.

Full regression, native Windows and independent review results are recorded after completion. No real owner records, connected account grants or live scheduled work were deleted to verify this feature.

The final author-run full check passed **1,369 tests without skips**, with the native read broker enabled. Native Windows passed **267 related tests** with two POSIX-only exclusions (symlink admission and retaining an open POSIX lease through unlink), both covered by the Linux run. After the final error-message/client-feedback correction, all **68 affected native lifecycle/browser tests** passed without skips and the app/engine/provider/contract source bytes matched the tested native copy. The coordinator and other native paths did not change after the 267-test run. A primary regression reproduced premature POSIX owner release before the fix; the corrected implementation holds ownership through removal and keeps owner files until other files are gone. Native rename-race coverage checks its distinct open-handle rule.

Rust, generated contracts, dependencies and native binaries were unchanged. The immediately preceding accepted restoration unit's independently rerun fmt, clippy, workspace and process-fixture results remain applicable. This is local synthetic verification, not release acceptance or proof of real phone/account delivery. Independent commit review is separate from the author-run results above.

The first independent review reproduced three gaps: explicit fresh startup inheriting background no-initialization mode, the same `AppRecords` instance lacking its root after erasure, and legitimate interrupted restoration barriers rejected for their two links. The amendment retains a durable, version-bound new-start intent through onboarding, recreates the empty recovery root, and normalizes only exact owned restoration barrier pairs before admission. It also accepts a Google configuration publication pair only when both links are in the same owned data directory; a link outside that scope still blocks deletion. Regression tests use real key/store creation, interrupted background onboarding, another restoration without app restart, both interrupted restoration barrier publications, and in-scope versus outside hard links.

The amended author-run full check passed **1,378 tests without skips**. Native Windows passed **277 related tests**, with only the same two POSIX-only exclusions, and complete source byte parity. These runs include all three review corrections and the bounded Google publication-pair handling.
